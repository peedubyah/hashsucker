## A. RANKING REACHABILITY

### Active Ranking Call Graph

```
Production request:
  API entry (POST /api/media-request, Seerr ingress)
    → media-request.js::searchByMedia()
      → cache.queryCandidatesByMedia(mediaId)
      → candidates.map(candidate => { ... manual rankingInput ... })    ← MANUAL construction
      → runLiveDiscovery() → liveCandidates.map(live => { ... manual rankingInput ... })  ← MANUAL
      → rankHitsTiered(rankingInputs, ...)
        → rankHits() per tier
          → rankHit() per hit
            → effectiveProviderAvailability = freshProviderAvailability + historicalPrior  ← 7e18b68 SEAM
      → cache.persistMediaRequest(intent, explainable)
        → INSERT INTO media_request_results (score, score_breakdown, ...)
```

### Answers

1. **Does historicalPrior reach the production path?**  
   **YES (after this slice).** Before this slice: **NO** — `searchByMedia` built ranking inputs manually with no `historicalPrior` field, so `rankHit()` saw `historicalPrior = 0` (default).

2. **Does media-request.js call `toRankingInput()`, or construct manually?**  
   **MANUAL construction.** It builds the ranking input object literal directly in the `.map()` callback.

3. **If manual, is historicalPrior absent?**  
   **Was absent.** Now added: `historicalPrior: computeHistoricalAvailabilityPrior(cache, infoHash, fileIndex)`.

4. **Does the persisted score/justification expose the historical contribution?**  
   **YES.** `rankHit()` exposes `justification.historicalPrior` and `justification.freshProviderAvailability`. The persisted `score_breakdown` reflects the effective providerAvailability (including prior). The `score` itself includes the bounded contribution.

5. **Is search-engine.js active for the same production request?**  
   **NO.** `search-engine.js::combinedSearch` serves the `/api/search` UI/debug route only. It is a **parallel, divergent implementation** — it uses `toRankingInput()` and has its own ranking machinery. It does NOT participate in the production `searchByMedia` path.

### Ranking Reachability Gap Patched

| Before | After |
|--------|-------|
| `searchByMedia` ranking inputs had `historicalPrior = 0` (default) | Both corpus and live ranking inputs now compute `historicalPrior` via `computeHistoricalAvailabilityPrior()` |
| Historical confidence only reached `/api/search` UI path | Historical confidence now reaches the production `/api/media-request` and Seerr ingress paths |

## B. PRIMARY PROVIDER-ORDER REACHABILITY

### Active Primary Provider Call Graph

```
Playback request (GET /api/playback/:mediaId):
  app.js::createRequestHandler()
    → existingSelection = searchCache.getExistingSelection(rawId)
    → if (rdClient && controlPlaneStore):
        → RD resolution cache hit → 307 redirect (RD)
        → RD resolution cache miss → attemptRdResolution() → 307 redirect (RD)
    → if RD failed/null:
        → revalidator.revalidateAvailability() (TorBox)
        → resolveTorBoxDeliverySeam() → 307 redirect (TorBox)
    → if TorBox fails:
        → tryAlternateCandidateFallback()  ← FALLBACK PATH
```

### Fallback Provider Call Graph

```
tryAlternateCandidateFallback():
  → alternateFallback.findUsableAlternate({ mediaId, primaryReleaseKey, expectedScope })
    → loadPersistedResults(mediaId, season, episode)
    → filterCandidates(results, ...)
    → for each candidate:
        → computeHistoricalProviderPrior(searchCache, infoHash, fileIndex)  ← NEW
        → determineProviderAttemptOrder(mergedPrior)
        → for each provider in attemptOrder:
            → torbox: revalidator.revalidateAvailability()
            → realdebrid: attemptRdResolutionFromAlternate()
```

### Answers

1. **Where is provider order chosen for the primary?**  
   **Hardcoded RD-first cascade in `app.js`:** `if (rdClient && controlPlaneStore) { ... RD ... }` then fall through to TorBox seam. **No dynamic reordering.** No historical-prior integration.

2. **Where is provider order chosen for fallback?**  
   **`alternate-fallback.js::findUsableAlternate`** via `determineProviderAttemptOrder(historicalProviderPrior)`.

3. **Does 7e18b68 only affect alternate-fallback.js?**  
   **YES** for provider ordering. The `determineProviderAttemptOrder` helper was only integrated into the alternate-fallback path.

4. **Is there a small shared provider-order seam both can consume?**  
   **YES now.** `computeHistoricalProviderPrior(cache, infoHash, fileIndex)` is a standalone helper in `confidence-projection.js` that produces `{ torbox, realdebrid }` bounded priors. The fallback path now consumes it per-candidate.

### Primary Provider-Order Decision

**The primary path's hardcoded RD-first cascade cannot consume the helper without invasive refactoring.** The primary path is structured as:
```js
if (rdClient && controlPlaneStore) { ... RD attempt ... }
// fall through to TorBox
```

Reordering this to consume historical priors would require:
- Moving the RD/TorBox decision into a shared helper
- Inverting the control flow to attempt providers in a dynamic order
- Preserving the existing "RD first when available" default

This is **out of scope** per the spec: "If primary ordering cannot consume the helper without invasive refactoring, report that and leave it alone."

**Decision: Leave primary ordering unchanged.** The fallback path now consumes the helper. Primary ordering remains hardcoded RD-first.

| Test | Result |
|------|--------|
| P5. No evidence → default order (TorBox first) | ✅ PASS |
| P6. RD historical only → RD attempted first | ✅ PASS |

## D. DEAD/OVERLAPPING PATHS

### search-engine.js Integration

**Production-relevant: NO (for ranking).**  
`search-engine.js::combinedSearch` serves the `/api/search` UI/debug route only. It uses `toRankingInput()` and has its own ranking machinery. It does NOT participate in the production `searchByMedia` path.

However, the `/api/search` route is a real (if secondary) endpoint that operators use for debugging. The `computeHistoricalAvailabilityPrior` integration there is **valid but not production-critical**.

### media-request.js Duplicates Ranking Assembly

**YES, partially.** Both `media-request.js` and `search-engine.js` build ranking inputs and call `rankHitsTiered`. But they serve different paths:
- `media-request.js`: production request path (Seerr ingress, playback handoff)
- `search-engine.js`: UI debug path (`/api/search`)

The duplication is intentional — `media-request.js` needs direct control over candidate assembly (identity eligibility, live discovery fallback) that `search-engine.js`'s `toRankingInput()` abstraction doesn't provide.

**Do NOT refactor.** The spec says "do not refactor merely because duplication exists."

### Provider-Order Logic Duplicated Between Primary and Fallback

**YES.** The primary path (app.js) hardcodes RD-first; the fallback path (alternate-fallback.js) uses `determineProviderAttemptOrder`. These are independent.

The shared seam is now `computeHistoricalProviderPrior()` — but only the fallback path consumes it. Primary path remains hardcoded.
