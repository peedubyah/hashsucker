# Historical Availability Prior — Ranking & Provider-Order Integration

## Status: COMPLETE

## Summary

Integrated the proven evidence-confidence projection into HashSucker ranking
and provider probe priority. The integration is conservative: historical
evidence is a **prior** that can modestly influence close candidates or
provider try-order, but fresh authoritative evidence always outranks it.

## Core Rule Enforced

Historical evidence is a prior. Fresh authoritative provider evidence
outranks it. No historical signal may:
- declare a cache hit
- create a placement
- create a capability
- bypass provider validation
- alter durable identity

## Ranking Integration

### Seam

The historical prior is folded into the existing `providerAvailability`
component (weight 0.10) rather than adding a new weight. This avoids
invasive recalibration and preserves the deterministic tie-break chain.

### Files Changed

1. **`src/lib/discovery/confidence-projection.js`**
   - Added `historicalAvailabilityPriorContribution(projection, options)` —
     standalone exported function that computes a bounded [0, 1] contribution
     from the evidence projection.
   - Added `computeHistoricalAvailabilityPrior(cache, infoHash, fileIndex, options)` —
     convenience wrapper that collects evidence from cache and computes the prior.
   - Both functions respect the precedence rules:
     - fresh positive → 0 (fresh dominates)
     - fresh negative → 0 (fresh suppresses optimism)
     - stale → 0 (stale alone cannot claim availability)
     - null → bounded prior (capped at `maxPrior=0.4`)
   - Corroboration bonus: +0.05 per additional corroboration family beyond
     the first, capped at `maxPrior`.

2. **`src/lib/discovery/ranking.js`**
   - `rankHit()` now accepts `historicalPrior` field (default 0).
   - Computes `effectiveProviderAvailability = freshProviderAvailability + historicalPrior`,
     clamped to [0, 1].
   - Exposes `historicalPrior` and `freshProviderAvailability` in the
     justification object for explainability.

3. **`src/lib/discovery/canonical.js`**
   - `toRankingInput()` now passes through `historicalPrior` field.

4. **`src/lib/discovery/search-engine.js`**
   - Imports `computeHistoricalAvailabilityPrior`.
   - Computes historical prior for each candidate before ranking.
   - Attaches prior to ranking input via `toRankingInput`.

### Weight/Bound/Decay Behavior

- **Weight**: Folded into existing `providerAvailability` weight (0.10).
- **Max prior**: 0.4 (configurable via `options.maxPrior`).
- **Corroboration bonus**: 0.05 per additional family, capped at maxPrior.
- **Decay**: Uses the projection's freshness decay (30-day half-life).
- **Precedence**: Fresh evidence always outranks historical.

### Precedence Rules

1. freshProvider='positive' → historical prior = 0
2. freshProvider='negative' → historical prior = 0
3. freshProvider='stale' → historical prior = 0
4. freshProvider=null → bounded prior ∈ [0, 0.4]

### Determinism

- No wall-clock dependence (pinned `now` passed through).
- No SQLite row-order dependence (evidence sorted by observedAt, then kind).
- No Map insertion-order dependence (uses sorted arrays).
- Shuffled evidence/candidate order produces byte-identical results.

## Provider-Order Integration

### Seam

The `findUsableAlternate()` function in `alternate-fallback.js` now accepts
a `historicalProviderPrior` parameter (`{ torbox: number, realdebrid: number }`).
This affects **try order only** — both providers are still attempted, and
eligibility/fulfillment semantics are unchanged.

### Files Changed

1. **`src/lib/resolver/alternate-fallback.js`**
   - Added `determineProviderAttemptOrder(historicalProviderPrior)` — pure
     function that returns `['torbox', 'realdebrid']` (default) or
     `['realdebrid', 'torbox']` when RD has a strictly higher prior.
   - Modified `findUsableAlternate()` to accept `historicalProviderPrior`
     and use it to determine attempt order.
   - Exposes `providerOrder` in the return value for telemetry.

### Ordering Rules

- No evidence for either → TorBox first (default)
- History for RD only → RD may be tried first
- History for both → stronger bounded projection chooses first
- History for A + fresh negative for A → A is NOT preferred (prior suppressed)
- Whichever provider goes second remains eligible for fallback

## Production Impact Estimate

### Ranking

- **Candidates with usable confidence evidence**: Depends on historical
  provider evidence ingestion volume. With the source-vs-snapshot repair
  at 1ac335c, each independent source contributes at most 0.20 to the prior.
- **Non-zero historical prior today**: Candidates with historical evidence
  AND no fresh provider observation. The prior is capped at 0.4, so the
  maximum score delta is 0.4 × 0.10 = 0.04.
- **Score-delta distribution**: Most candidates will see 0 (no history or
  fresh evidence present). Candidates with history but no fresh evidence
  will see a modest boost of 0.01-0.04.
- **Corpus reorder risk**: Low. The 0.04 max delta is smaller than typical
  quality/relevance differences (0.1-0.3), so history will not overturn
  materially better candidates.

### Provider Order

- **Effect**: Only changes which provider is tried first for a selected
  candidate. Both providers are still attempted.
- **Fallback preservation**: The second provider remains fully eligible
  for fallback. No provider is excluded.
- **API call impact**: No additional API calls. The historical prior is
  computed from the existing evidence store.

## Explanation / Telemetry

The ranking justification now exposes:
- `historicalPrior`: the bounded contribution added to providerAvailability
- `freshProviderAvailability`: the fresh evidence component

Example explanation:
```
Candidate received +0.02 because RD had historical evidence from 2 independent sources / 3 distinct snapshots
```

The provider-order return value exposes:
- `providerOrder`: the ordered array of providers (e.g., `['realdebrid', 'torbox']`)

Example explanation:
```
RD was attempted before TorBox because historical provider prior was higher
```
