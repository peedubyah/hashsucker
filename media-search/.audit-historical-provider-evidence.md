# Audit + Implementation Report: Historical Provider Evidence Landing Zone

**Scope:** Persist durable historical provider evidence ("Real-Debrid has
seen/served this release before") as a persistent prior for confidence
projection. This is a **landing zone only** — no scraper, no downloader,
no giant RD list import. This slice builds the durable storage and the
API contract for future large imports.

This is **NOT** current cache hit, current placement, current availability,
or current delivery capability. History is a prior.

## 1. Existing storage audit

### `provider_observation_current`

- **Schema:** singleton per `(provider, account_scope, scope, subject_type, subject_key, kind)`. `info_hash` / `file_index_key` are non-PK payload columns.
- **Semantics:** "current truth for this search subject." The row is overwritten when a newer `observed_at` arrives. NOT append-only history.
- **Can it represent historical provider evidence?** No. Changing its semantics would destroy current-period availability semantics. The PK identity is `(provider, account_scope, scope, subject_type, subject_key, kind)` — not `(infoHash, fileIndexKey)` at the identity level.

### `provider_observation_events`

- **Schema:** append-only event log with `id` as synthetic PK. Columns include `info_hash`, `file_index_key`, `provider`, `state`, `observed_at`, `expires_at`, `source`, `error_category`.
- **Semantics:** "every provider probe attempt." State is `cached | uncached | error | unknown` — a probe result, not a corpus membership signal.
- **Can it represent historical provider evidence?** It can technically store the raw events, but it conflates probe results with corpus membership signals. It has no `(source_id, source_version)` axis for identifying distinct historical snapshots. It is indexed for probe routing, not for corpus-scoped queries. The confidence projection already reads from this table via `getProviderObservations()` for fresh/stale signals — reusing it for historical would blur the two axes.

### `dmm_source_observations`

- **Schema:** `(info_hash, file_index_key, source, fragment_name, generation_id)`. No `provider` column. No `state` column.
- **Semantics:** "DMM fragment membership." Entirely different evidence axis.
- **Can it represent historical provider evidence?** No. Wrong identity columns and wrong domain.

### `corpus_observations` (evidence-projection.js)

- **Schema:** append-only log with `observed_at`, `source`, `ingestion_id`, `fragment_id`, `corpus_version_id`, `evidence`. No `provider` column. `source` is used generically.
- **Can it represent historical provider evidence?** Close, but conflates DMM corpus evidence with provider evidence. The `source` field would need a convention (provider name = source, state in `evidence` JSON). But it has no `(provider, source_id, source_version)` axis for idempotent giant imports.

### `candidates.sources`

- **Schema:** JSON array on `candidates` table. Discovery source tags, not provider availability signals. No temporal axis, no per-provider breakdown.
- **Can it represent historical provider evidence?** No. Orthogonal concept.

### Decision: new dedicated table

`provider_observation_current` is wrong because it's "current truth" and overwrites. `provider_observation_events` is a probe log, not a corpus membership store. The historical prior requires a separate table with a different identity axis, different retention lifecycle, and different read semantics.

## 2. New schema

```sql
CREATE TABLE IF NOT EXISTS historical_provider_evidence (
  info_hash           TEXT NOT NULL,
  file_index_key      INTEGER NOT NULL DEFAULT -1,
  provider            TEXT NOT NULL,
  account_scope       TEXT,
  evidence_type       TEXT NOT NULL,
  source_id           TEXT NOT NULL,
  source_version      TEXT NOT NULL DEFAULT '',
  first_seen_at      INTEGER NOT NULL,
  last_seen_at       INTEGER NOT NULL,
  observation_count   INTEGER NOT NULL DEFAULT 1,
  PRIMARY KEY (info_hash, file_index_key, provider,
               evidence_type, source_id, source_version)
);

CREATE INDEX IF NOT EXISTS idx_historical_provider_evidence_candidate
  ON historical_provider_evidence(info_hash, file_index_key);
CREATE INDEX IF NOT EXISTS idx_historical_provider_evidence_source
  ON historical_provider_evidence(provider, source_id, source_version);
```

**Key design choices:**
- `file_index_key = -1` is the canonical release-level coordinate (matches `dmm_source_observations` convention).
- `file_index_key = N` (N ≥ 0) is used only when a source genuinely provides a trustworthy file-level coordinate.
- `account_scope` is nullable — many historical sources are not account-scoped.
- `evidence_type` is `'historical_hit'` in this slice. Taxonomy intentionally not expanded.
- `source_version` defaults to `''` for callers that don't track versions. It is part of the PK so that a deliberate schema change in the source creates a new row rather than silently overwriting.
- `metadata_json` is intentionally absent. URLs, filenames, ordinals are not persisted.

## 3. Unique / idempotency key

**PK:** `(info_hash, file_index_key, provider, evidence_type, source_id, source_version)`

**Upsert logic:**
```sql
INSERT INTO historical_provider_evidence
  (info_hash, file_index_key, provider, account_scope, evidence_type,
   source_id, source_version, first_seen_at, last_seen_at, observation_count)
VALUES (...)
ON CONFLICT(info_hash, file_index_key, provider, evidence_type,
             source_id, source_version)
DO UPDATE SET
  first_seen_at    = MIN(first_seen_at, excluded.first_seen_at),
  last_seen_at    = MAX(last_seen_at, excluded.last_seen_at),
  observation_count = observation_count + excluded.observation_count,
  account_scope    = COALESCE(account_scope, excluded.account_scope);
```

**Idempotency properties:**
- One giant snapshot imported twice → `observation_count` increases, row count unchanged.
- Same release in a later snapshot → `last_seen_at` advances, `observation_count` increases.
- Same release from a new independent source_id → new PK row (distinct corroboration signal preserved).
- Re-import with earlier `last_seen_at` → absorbed by `MAX`, does not rewind timestamps.

## 4. Release-level vs file-level semantics

The `file_index_key = -1` convention is used for release-level evidence (the source proves "this infoHash existed" without naming a specific file). The table supports file-level evidence via `file_index_key ≥ 0`, but this does NOT manufacture a `TorrentFile` identity. File-level evidence is stored as candidate evidence only.

**Identity invariant:** The storage API never manufactures `TorrentFile` identity from `source_id`, `info_hash`, `file_index_key`, filename, or URL. A `file_index_key ≥ 0` row is treated as candidate-scoped evidence, not as a `TorrentFile` row.

## 5. Current-vs-historical separation

| | Fresh provider observation | Historical provider evidence |
|---|---|---|
| **Table** | `provider_observation_events` / `_current` | `historical_provider_evidence` |
| **Semantic** | "is it cached RIGHT NOW?" | "has it been seen before?" |
| **TTL** | expiresAt (minutes to hours) | unbounded (survives negative) |
| **Lifespan** | Short — overwritten or expires | Persistent — survives uncached |
| **Reads via** | `getProviderObservations()` | `getHistoricalProviderEvidence()` |
| **Projection kind** | `PROVIDER_FRESH_POSITIVE/NEGATIVE/STALE` | `PROVIDER_HISTORICAL` |
| **API names** | `appendProviderObservation()` | `ingestHistoricalProviderEvidence()` |

Historical evidence is NEVER deleted because a provider reports uncached. Fresh negative outranks historical prior for current interpretation; historical evidence SURVIVES the negative reading.

## 6. Confidence projection integration

### New evidence kind: `PROVIDER_HISTORICAL` (extended)

The `PROVIDER_HISTORICAL` kind already existed in session 5's projection for observations from `provider_observation_events`. This slice extends it:

**From `historical_provider_evidence`:** one `PROVIDER_HISTORICAL` item per distinct `(provider, source_id, source_version)` row is emitted via `getHistoricalProviderEvidence()` in `collectObservations`.

**Per-source family for corroboration:** each historical row carries `historicalSourceId = "${provider}:${source_id}:${source_version}"`. The `classify()` function returns `FAMILY_PROVIDER:${historicalSourceId}` as the family. This means two independent historical sources (e.g. `rd-history-2024` and `rd-history-2023`) are two distinct corroboration families, raising `corroboration` from 1 to 2.

**availabilityPrior deduplication:** `providerHistoricalSources = new Set()` ensures each unique historical source contributes +0.20 to `availabilityPrior` once, not amplified by re-imports.

**Precedence:**
- Fresh RD negative (`PROVIDER_FRESH_NEGATIVE`) → `freshProvider = 'negative'`
- Fresh RD positive (`PROVIDER_FRESH_POSITIVE`) → `freshProvider = 'positive'`
- Historical RD (`PROVIDER_HISTORICAL`) → survives in `reasons`, raises `availabilityPrior`
- All-stale penalty applies if only historical stale evidence remains

### Bug fix in `collectObservations` (pre-existing)

The state derivation for provider observations had an operator-precedence bug:
```js
// BROKEN: ?? has lower precedence than ===, so this always returned 'cached'
// for any non-nullish state
const state = (o.state ?? o.cached === true ? 'cached' : ...);

// FIXED: explicit if/else, no precedence ambiguity
if (typeof o.state === 'string') state = o.state;
else if (o.cached === true) state = 'cached';
else if (o.cached === false) state = 'uncached';
else state = 'unknown';
```

### Bug fix: `getProviderObservations` now accepts `now` parameter

The projection now passes `options.now` through to `getProviderObservations`. Previously, the projection pinned `now` but the cache read used `Date.now()` (real wall clock), making the freshness of cached observations dependent on the wall clock rather than the projection's pinned clock. This fix ensures full determinism when `now` is pinned.

## 8. Production corpus analysis (rough estimates)

**Assumptions:**
- `info_hash TEXT NOT NULL` = 40 bytes + overhead ≈ 60 bytes average
- `provider TEXT NOT NULL` = 15 bytes average
- `source_id TEXT NOT NULL` = 30 bytes average
- `source_version TEXT NOT NULL DEFAULT ''` = 5 bytes average
- Other columns ≈ 40 bytes
- Row overhead (SQLite B-tree, record header) ≈ 20 bytes
- Index on `(info_hash, file_index_key)` ≈ 50 bytes per entry
- Index on `(provider, source_id, source_version)` ≈ 55 bytes per entry

**Per-row storage:** ~165 bytes + 105 bytes indexes ≈ **270 bytes per row**

| Row count | Table size (est.) | Index size (est.) | Total (est.) |
|---|---|---|---|
| 1M | 165 MB | 105 MB | **~270 MB** |
| 5M | 825 MB | 525 MB | **~1.35 GB** |
| 10M | 1.65 GB | 1.05 GB | **~2.7 GB** |

**Existing candidates join:** `idx_candidates(info_hash, file_index_key)` already exists and supports efficient joins. The `idx_historical_provider_evidence_candidate` uses the same column order, making the join efficient.

**Existing indexes:** The current `provider_observation_events` index `idx_provider_observation_events_candidate` covers `(info_hash, file_index_key, provider, observed_at DESC)`. The new `idx_historical_provider_evidence_candidate` covers `(info_hash, file_index_key)` directly (simpler, no provider column in key). These are compatible with the same join strategy.
