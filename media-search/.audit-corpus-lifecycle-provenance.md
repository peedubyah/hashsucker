## 1. Lifecycle / state-machine map

### Before this work

```
DMM HashList source
  └─ listFragments() returns { fragments, treeSha, branch }
       └─ runner.run()
            └─ for each fragment:
                 └─ stream → ingestCandidates() → flushBatch() (transactional)
                      └─ candidates + release_attributes + FTS (atomic post-f669235)

  dmm_ingestion_runs: 1 row, status='incomplete', tree_sha=NULL-derived
  dmm_fragments: 14,534 rows (status='complete'|'failed'|'no_payload')
  candidates.sources: JSON metadata only, no fragment_id, no tree_sha
  NO observation table linking (info_hash, file_index_key) → fragment/generation
  NO refresh-generation concept; refresh = re-ingest = duplicate observations
```

**Missing:**
- No generation identity per refresh
- No per-(candidate, source, fragment, generation) observation record
- No way to ask "which candidates disappeared in the last refresh?"
- No way to ask "which candidates are still justified by another source?"

### After this work

```
DMM HashList source
  └─ listFragments() returns { fragments, treeSha, branch }
       └─ runner.run(generationId=treeSha, treeSha=treeSha)
            ├─ cache.startDmmGeneration({ generationId: treeSha, source: 'dmm-hashlist' })
            ├─ for each fragment:
            │    └─ stream → ingestCandidates({ fragmentName, generationId })
            │         └─ recordDmmSourceObservations(...)  (per-candidate, per-fragment, per-gen)
            │         └─ flushBatch() (transactional, atomic post-f669235)
            └─ cache.completeDmmGeneration(generationId, 'complete'|'incomplete'|'failed')

  dmm_ingestion_generations: one row per refresh, status='running'→'complete'/'incomplete'/'failed'
  dmm_source_observations: one row per (info_hash, file_index_key, source, fragment, generation)
  candidates.sources: unchanged (provenance metadata, never identity)
  refresh-generation: treeSha is the generation_id; "current generation" = status='complete' with max completed_at
```

**Added:**
- Refresh-generation concept keyed on `treeSha`
- Many-to-many observation table: a candidate can be justified by many
  (source, fragment, generation) tuples
- Stale-detection queries: `findStaleObservations`, `findStaleFragments`,
  `findPruneEligibleCandidates`, `findPruneEligibleAttributes`
- Justification query: `getDmmObservationsForCandidate` surfaces all observations
  across all sources and generations for a single candidate identity

### State machine for `dmm_ingestion_generations.status`

```
   startDmmGeneration()
          │
          ▼
      ┌─────────┐
      │ running │
      └────┬────┘
           │  completeDmmGeneration(status='complete')   zero failures
           │  completeDmmGeneration(status='incomplete') 1+ failures
           │  completeDmmGeneration(status='failed')     fatal error caught
           ▼
   complete / incomplete / failed
           │
           ▼
       (terminal)
```

`incomplete` is set when ≥1 fragment failed but the run reached the
post-loop step. `failed` is set in the catch block on a fatal exception.
Only `complete` is used for stale detection (see §6).

## 3. Concrete defects

### D1 — No per-fragment resume checkpoint [REPORT-ONLY]

**Defect:** `DmmIngestionRunner.processFragment()` does not persist a
checkpoint. If the process crashes mid-fragment, the entire run restarts from
the top of the fragment list. The post-f669235 atomic batch makes this safe
(idempotent re-ingest), but it wastes work on large fragments.

**Decision:** Not patched in this slice. The new generation table records
`fragments_complete` and `fragments_failed`, so a future resumer can compare
`dmm_fragments.status` against the `dmm_ingestion_generations.fragments_complete`
counter. Implementing the resume would require:
1. Pre-run snapshot of `dmm_fragments.status` for the planned tree
2. Skipping fragments with `status='complete'`
3. Updating generation counters to reflect skips

### D2 — generationId not defined in constructor [PATCHED]

**Defect:** `DmmIngestionRunner` constructor destructured `treeSha` but not
`generationId`, so `this.pinnedGenerationId` was `undefined`. The runner code
that reads `this.pinnedGenerationId` to pass to `startDmmGeneration()` would
have crashed.

**Fix:** Added `generationId = null` and `treeSha = null` to the destructured
constructor parameters. Both are pinned as `this.pinnedGenerationId` and
`this.pinnedTreeSha`. Verified by re-running the full `dmm-ingestion` test
suite: 31 existing tests + 9 new provenance tests = 40 tests, all green.

### D3 — Stale-source lifecycle absent [PARTIALLY ADDRESSED]

**Defect:** Before this work, there was no way to identify which candidates
were "no longer seen" by DMM. Refreshing the corpus could only over-write or
skip; it could not mark candidates as stale.

**Fix:** Added the `dmm_source_observations` table and the stale-detection
queries. **Destructive pruning (`DELETE`) is intentionally NOT implemented in
this slice** per the user's instruction. The `findPruneEligibleCandidates` and
`findPruneEligibleAttributes` queries are exposed on the cache API so a
follow-up "prune phase" can wire them in safely.

### D4 — `treeSha` returned but never persisted in-tree [PATCHED]

**Defect:** `HashListSource.listFragments()` already returns
`{ fragments, treeSha, branch }`. The runner discarded `treeSha` and called
`dmm_ingestion_runs` with whatever the in-script tree was. This meant the
authoritative DMM tree SHA — the natural generation identity — was not
recorded anywhere queryable from the corpus DB.

**Fix:** `DmmIngestionRunner` now captures `treeSha` from `listFragments()`,
pins it as `this.pinnedTreeSha`, and passes it to:
- `startDmmGeneration({ generationId, treeSha, source })` — the new
  `dmm_ingestion_generations` row carries `tree_sha`.
- `recordDmmSourceObservations({ generationId, ... })` — every observation is
  tagged with `generation_id = treeSha`.

The `dmm_ingestion_runs` table is left untouched (legacy schema, will be
decommissioned once `dmm_ingestion_generations` is validated end-to-end).

### D5 — Same-millisecond `completed_at` non-determinism [PATCHED]

**Defect:** When two or more `dmm_ingestion_generations` rows are marked
`complete` in the same millisecond (e.g. a test that completes G1 and G2
back-to-back), their `completed_at` columns are equal. `ORDER BY completed_at
DESC LIMIT 1` then returns an arbitrary row, making "current complete
generation" non-deterministic.

**Fix:** The `GET_CURRENT_COMPLETE_GENERATION` query is now:
```sql
SELECT * FROM dmm_ingestion_generations
WHERE source = ? AND status = 'complete'
ORDER BY completed_at DESC, rowid DESC
LIMIT 1;
```
The `rowid DESC` tiebreaker makes the ordering deterministic when
`completed_at` values are equal. (Alternative considered: fabricate
millisecond-different timestamps in tests. The query fix is more robust.)

### D6 — `dmm_ingestion_runs.status='incomplete'` [NOT A BUG]

**Concern:** The single production run shows `status='incomplete'` with
`completed_at=NULL`. This looked like a defect — the run was never marked
complete.

**Verdict:** Correct behavior. 13 of 14,534 fragments failed (all
`error='no_payload'`), and the run logic correctly sets `status='complete'`
only when zero fragments failed. With 13 failures, the honest status is
`incomplete`. The new `dmm_ingestion_generations.status` mirror this exact
contract: `'complete'` = all fragments OK, `'incomplete'` = ≥1 fragment
failed, `'failed'` = fatal exception. No code change.

This is now documented in the `dmm_ingestion_generations` schema CHECK
constraint:
```sql
status CHECK (status IN ('running', 'complete', 'incomplete', 'failed'))
```

### D7 — FK enforcement on `dmm_source_observations` [REPORT-ONLY]

**Defect:** `dmm_source_observations` does not have FK constraints to
`candidates`, `dmm_ingestion_generations`, etc. A row could exist for a
candidate identity that does not exist (referential integrity would have to
be enforced by application logic).

**Decision:** Not patched. Reasons:
1. SQLite `node:sqlite` does not enforce FKs by default; they require
   `PRAGMA foreign_keys=ON` per connection.
2. The cache opens many short-lived connections; managing FK enablement is a
   separate concern.
3. The new observation table is the source of truth for "what was seen" and
   can tolerate orphan rows for a short window (candidates are upserted in
   the same transaction as observations).

A follow-up could add `PRAGMA foreign_keys=ON` to the cache factory and FK
constraints to the new table for defense in depth.

## 4. Schema added

```sql
CREATE TABLE IF NOT EXISTS dmm_ingestion_generations (
  generation_id      TEXT PRIMARY KEY,
  source             TEXT NOT NULL,
  tree_sha           TEXT,
  started_at         INTEGER NOT NULL,
  completed_at       INTEGER,
  fragments_total    INTEGER NOT NULL DEFAULT 0,
  fragments_complete INTEGER NOT NULL DEFAULT 0,
  fragments_failed   INTEGER NOT NULL DEFAULT 0,
  records_seen       INTEGER NOT NULL DEFAULT 0,
  status             TEXT NOT NULL
    CHECK (status IN ('running', 'complete', 'incomplete', 'failed'))
);

CREATE TABLE IF NOT EXISTS dmm_source_observations (
  info_hash      TEXT NOT NULL,
  file_index_key INTEGER NOT NULL,
  source         TEXT NOT NULL,
  fragment_name  TEXT NOT NULL,
  generation_id  TEXT NOT NULL,
  first_seen_at  INTEGER NOT NULL,
  last_seen_at   INTEGER NOT NULL,
  records_seen   INTEGER NOT NULL DEFAULT 1,
  PRIMARY KEY (info_hash, file_index_key, source, fragment_name, generation_id)
);
CREATE INDEX IF NOT EXISTS idx_dso_source_gen
  ON dmm_source_observations(source, generation_id);
CREATE INDEX IF NOT EXISTS idx_dso_gen
  ON dmm_source_observations(generation_id);
CREATE INDEX IF NOT EXISTS idx_dso_info_hash
  ON dmm_source_observations(info_hash, file_index_key);
```

### Identity preserved

- `candidates` PK unchanged: `(info_hash, file_index_key)`.
- `release_attributes` PK unchanged: `(info_hash, file_index_key, source)`.
- `candidates.sources` JSON unchanged: provenance metadata, never identity.
- The new `dmm_source_observations` PK includes `(info_hash, file_index_key)`,
  so observation tuples are anchored to the same candidate identity.
- `file_index_key = -1` continues to mean NULL `fileIndex` (torrent-level).
  Per-file candidates would use 0, 1, 2, ...

### No `ALTER TABLE` on existing tables

The two new tables are purely additive. No `candidates`, `release_attributes`,
or `dmm_fragments` schema changed. No data migration required.

## 5. Idempotency key

**`dmm_source_observations` PK:**

```text
(info_hash, file_index_key, source, fragment_name, generation_id)
```

This composite key gives the desired idempotency:

1. **Re-running the same generation against the same fragment is a no-op.**
   The `INSERT OR IGNORE` skips already-existing rows; the subsequent
   `UPDATE ... SET last_seen_at = MAX(last_seen_at, ?), records_seen = records_seen + 1`
   "touches" the existing row, incrementing `records_seen` if the same
   (candidate, source, fragment, generation) is observed again. The
   `records_seen` counter is the audit trail for "how many times did this
   (source, fragment) report this candidate in this generation?"

2. **Re-running a generation does not amplify rows.** The number of rows
   in `dmm_source_observations` is bounded by:
   `|candidates| × |sources_per_candidate| × |fragments_per_source| × |generations|`.
   In production, `sources_per_candidate` is 1 and `fragments_per_source` is 1
   per generation, so the bound is approximately `|candidates| × |generations|`.

3. **Test 2 ("G1 ingest is idempotent") proves the no-amplify property.**
   It records the same `(info_hash, source, fragment, generation)` twice
   and asserts that row count is unchanged.

## 6. Stale-detection queries

### `findStaleObservations(prev, current)`

```sql
SELECT info_hash, file_index_key, source, fragment_name, generation_id
FROM dmm_source_observations
WHERE generation_id = @prev_generation
EXCEPT
SELECT info_hash, file_index_key, source, fragment_name, generation_id
FROM dmm_source_observations
WHERE generation_id = @current_generation;
```

Surfaces `(candidate, source, fragment)` tuples that were observed in
`prev` but are absent from `current`. Safe to call while `current` is still
`running` (results are partial until `current` is marked `complete`).

### `findStaleFragments(prev, current)`

```sql
SELECT DISTINCT source, fragment_name
FROM dmm_source_observations
WHERE generation_id = @prev_generation
EXCEPT
SELECT DISTINCT source, fragment_name
FROM dmm_source_observations
WHERE generation_id = @current_generation;
```

Identifies fragment names that disappeared between generations. This is the
authoritative answer to "which DMM tree fragments were removed?"

### `findPruneEligibleCandidates(current)`

```sql
SELECT c.info_hash, c.file_index_key
FROM candidates c
WHERE NOT EXISTS (
  SELECT 1 FROM dmm_source_observations o
  WHERE o.info_hash = c.info_hash
    AND o.file_index_key = c.file_index_key
    AND o.generation_id = @current_generation
);
```

Source-AGNOSTIC: a candidate is NOT prune-eligible if ANY source observed it
in the current generation. This is the safe default — a candidate is
deleted only when NO source (DMM, scraper, manual import) saw it.

### `findPruneEligibleAttributes(current)`

Same shape for `release_attributes`. Attributes without any source
observation justifying them in the current generation are listed.

### `getDmmObservationsForCandidate(info_hash, file_index_key)`

```sql
SELECT source, fragment_name, generation_id,
       first_seen_at, last_seen_at, records_seen
FROM dmm_source_observations
WHERE info_hash = @info_hash
  AND file_index_key = @file_index_key
ORDER BY generation_id DESC, source, fragment_name;
```

Justification view: a single candidate identity may have been observed by
many `(source, fragment, generation)` tuples over time. A justification-aware
prune layer consults this view to decide whether a candidate is
globally stale.

### `getCurrentDmmGeneration(source)`

```sql
SELECT * FROM dmm_ingestion_generations
WHERE source = ? AND status = 'complete'
ORDER BY completed_at DESC, rowid DESC
LIMIT 1;
```

The authoritative "current complete generation for source X". The
`rowid DESC` tiebreaker handles the same-millisecond case (D5).

### Stale-detection status

Only `status='complete'` rows are used as `@current_generation`. An
`incomplete` or `running` generation is never trusted for stale detection,
because its observations are partial.

## 7. Interrupted-refresh behavior

### Scenario: G1 is complete, G2 is interrupted

```
G1: complete   → dmm_source_observations has rows for the candidates G1 saw
G2: incomplete → started_at is set, fragments_complete=12, fragments_failed=3,
                  completed_at is NULL
```

**Behavior:**

1. `findPruneEligibleCandidates(G1)` returns no candidates that G1 saw
   (they all have an observation in G1).
2. `findPruneEligibleCandidates(G2)` returns no candidates that G2 saw
   (partial, but correct: every candidate that G2 saw has an observation).
3. `findStaleObservations(G1, G2)` returns G1 observations that did not
   reappear in G2. Because G2 is partial, this set is over-inclusive —
   it includes candidates that G2 simply did not get to before the
   interruption. **This is why stale detection must use a `complete` G2.**
4. `getCurrentDmmGeneration('dmm-hashlist')` returns G1 (not G2) because
   G2 is not `status='complete'`. The user can safely re-run the refresh
   without G2 polluting the "current" view.

### Scenario: G2 is interrupted and re-run completes

```
G2: complete (re-run) → completed_at set, fragments_complete=14,534
```

**Behavior:**

1. G1 observations are unchanged. A candidate that was in G1 but not in
   G2 (re-run) is now queryable via `findStaleObservations(G1, G2)`.
2. `getCurrentDmmGeneration('dmm-hashlist')` returns G2 (re-run).
3. `findPruneEligibleCandidates(G2)` returns the candidates that G1 saw
   but G2 (re-run) did not. This is the "safe to delete" set, gated on
   the re-run reaching `complete`.

### Scenario: A candidate appears in G1 and G2

```
candidate X has observations:
  (X, -1, 'dmm-hashlist', 'frag-A', G1)
  (X, -1, 'dmm-hashlist', 'frag-B', G2)
```

`findPruneEligibleCandidates(G2)` does NOT return X (X has a G2
observation). `findStaleObservations(G1, G2)` does NOT return X
(EXCEPT semantics). This is correct: X is justified in G2.

### Test 4 ("interrupted G2 does not mark G1 observations stale") proves
this empirically. It records G1, starts but does NOT complete G2, then
asserts that `getCurrentDmmGeneration` returns G1.

## 8. Run-completion analysis (D6)

**Observation:** The single production `dmm_ingestion_runs` row has
`status='incomplete'` and `completed_at=NULL`.

**Verdict:** NOT A BUG. The 13/14,534 fragments that failed (all
`error='no_payload'`) correctly produce a non-`complete` status. The
runner code sets `status='complete'` only when zero fragments failed.
With 13 failures, the honest status is `incomplete`.

**Schema CHK** on the new `dmm_ingestion_generations.status`:
```sql
CHECK (status IN ('running', 'complete', 'incomplete', 'failed'))
```
The four-state contract is documented in the column comment and matches
the legacy `dmm_ingestion_runs` behavior.

**No code change.** The legacy table is left in place; the new table
records the same lifecycle with finer-grained counters
(`fragments_complete`, `fragments_failed`).

## 10. Production backfill estimate

The new `dmm_source_observations` table is empty in production
(pre-existing data has no fragment↔candidate linkage). A backfill would
create observations for the 1.48M existing candidates.

**Backfill strategy:** For each candidate, insert ONE observation row
using the production `tree_sha` as the `generation_id` and
`fragment_name='unknown'` (the corpus does not record which fragment
produced which candidate).

### Row-count estimate

| design | row count | bytes (rough) | comment |
|---|---|---|---|
| fragment-sparse: 1 obs per (candidate, source, generation) | 1.48M | ~150 MB | **recommended** |
| fragment-complete: 1 obs per (candidate, source, fragment, generation) | 1.48M × 14,534 = 21.5B | ~2.1 TB | impractical |

The fragment-sparse design is the only practical option. It captures the
minimum useful provenance: "this candidate was observed by the DMM source
in this generation." Fragment-level provenance can be added incrementally
by re-running the runner with fragment-level recording enabled.

### SQL sketch (manual one-shot)

```sql
INSERT OR IGNORE INTO dmm_source_observations
  (info_hash, file_index_key, source, fragment_name, generation_id,
   first_seen_at, last_seen_at, records_seen)
SELECT
    c.info_hash,
    c.file_index_key,
    'dmm-hashlist'  AS source,
    'unknown'        AS fragment_name,
    'fda7edc62d85d1021492d2767cd5af9080fc922f' AS generation_id,
    strftime('%s','now') * 1000 AS first_seen_at,
    strftime('%s','now') * 1000 AS last_seen_at,
    1                AS records_seen
FROM candidates c;
```

The `INSERT OR IGNORE` is a no-op for any candidate that already has an
observation in the same generation (idempotent). The query is a single
sequential scan over `candidates`; on the production DB, ~1.48M rows
insert in well under a minute on a warm cache.

### Backfill also requires

1. **One `dmm_ingestion_generations` row** for the production tree_sha:
   ```sql
   INSERT OR REPLACE INTO dmm_ingestion_generations
     (generation_id, source, tree_sha, started_at, completed_at,
      fragments_total, fragments_complete, fragments_failed, records_seen, status)
   VALUES
     ('fda7edc62d85d1021492d2767cd5af9080fc922f', 'dmm-hashlist',
      'fda7edc62d85d1021492d2767cd5af9080fc922f', 1787868272445, NULL,
      14534, 14521, 13, 27267498, 'incomplete');
   ```
   `completed_at=NULL` is correct: the legacy run never set it.

2. **No schema migration**: tables are additive.

3. **WAL consideration**: enable WAL on the production DB before the
   bulk insert (`PRAGMA journal_mode=WAL;`) for concurrent readers.

### Out-of-scope

- **Destructive pruning** is NOT executed in this slice. The backfill only
  records provenance; it does not delete any candidate.
- **The legacy `dmm_ingestion_runs` table** is left untouched. It can be
  deprecated in a follow-up once `dmm_ingestion_generations` is validated
  end-to-end.
- **The `dmm_hash_prevalence` table** (1.48M rows, populated by a
  standalone prevalence script) is unrelated to the new observation
  table. It records hash prevalence across time, not per-generation
  provenance.
