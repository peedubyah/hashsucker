# Historical Provider Evidence — Snapshot/Replay Repair

This audit describes the minimum correction to the historical-provider
evidence landing zone added in `dd0317f`, addressing the two semantic
defects called out in the slice brief.

## 1. Previous semantic defect

The previous slice (commit `dd0317f`) had two compounding defects:

### 1.1 Replay was not idempotent

- **PK**: `(info_hash, file_index_key, provider, evidence_type, source_id, source_version)`
- **Upsert math**: `observation_count = observation_count + excluded.observation_count`
- **Effect**: Replaying the same snapshot version bumps
  `observation_count` arbitrarily. An operator running the same export
  N times can strengthen the evidence row N-fold. This is exactly what
  the spec forbids — replay must NOT create or strengthen evidence.

### 1.2 Source version leaked into corroboration families

- `confidence-projection.js` constructed
  `historicalSourceId = ${provider}:${source_id}:${source_version}`.
- `classify()` returned `family: ${FAMILY_PROVIDER}:${historicalSourceId}`,
  so `rd-history-2024/v1` and `rd-history-2024/v2` produced TWO
  corroboration families — a single independent source falsely split
  into two.

### 1.3 Source version doubled as row identity and snapshot identity

The PK mixed the **independent-source identity** (`source_id`) with the
**snapshot identity** (`source_version`). They are different concepts
and must be modeled separately.

### 1.4 infoHash validation broadened without v2 support

`isValidInfoHash()` accepted 64-char SHA-256 even though the rest of
HashSucker's candidate pipeline uses 40-char SHA-1. This would let
historical evidence rows exist that cannot be joined to a `candidates`
row.

## 2. Corrected source-vs-snapshot model

Two tables, deliberately layered:

### 2.1 `historical_provider_evidence_sightings` (the idempotency boundary)

```
PK (info_hash, file_index_key, provider, evidence_type, source_id, source_version)
```

A row exists iff THIS `(source_id, source_version)` snapshot reports
THIS sighting. Replay of the same snapshot is a no-op
(`INSERT OR IGNORE`).

| column          | semantics                                                |
| --------------- | -------------------------------------------------------- |
| info_hash       | 40-char SHA-1 lowercase                                  |
| file_index_key  | canonical coordinate; -1 = release-level                 |
| provider        | provider name (e.g. 'realdebrid')                        |
| evidence_type   | type of evidence (default 'historical_hit')              |
| source_id       | independent witness/source identity                      |
| source_version  | version/snapshot of that source (REQUIRED, non-empty)    |
| first_seen_at   | per-snapshot first-seen                                  |
| last_seen_at    | per-snapshot last-seen                                   |
| observation_count | per-snapshot delta (preserved per-snapshot)            |

### 2.2 `historical_provider_evidence` (the aggregate)

```
PK (info_hash, file_index_key, provider, evidence_type, source_id)
```

Source version is NOT in the key. One row per independent source
identity. Recomputed deterministically from the sightings table.

| column                     | semantics                                       |
| -------------------------- | ----------------------------------------------- |
| info_hash                  | 40-char SHA-1 lowercase                         |
| file_index_key             | canonical coordinate; -1 = release-level        |
| provider                   | provider name                                   |
| account_scope              | COALESCE-preserved (first non-null wins)        |
| evidence_type              | type of evidence                                |
| source_id                  | independent witness/source identity             |
| first_seen_at              | MIN(first_seen_at) across sightings             |
| last_seen_at               | MAX(last_seen_at) across sightings              |
| distinct_snapshot_count    | COUNT(*) of sightings for this identity         |

### 2.3 `historicalSourceId` construction

`confidence-projection.js` now builds
`historicalSourceId = ${provider}:${source_id}` — distinct versions of
the same source collapse to ONE corroboration family.

## 3. Idempotency keys

Two keys, one for each table:

| table                                         | key                                                                |
| --------------------------------------------- | ------------------------------------------------------------------ |
| `historical_provider_evidence_sightings`      | `(info_hash, file_index_key, provider, evidence_type, source_id, source_version)` |
| `historical_provider_evidence` (aggregate)   | `(info_hash, file_index_key, provider, evidence_type, source_id)`  |

The sightings key is the **replay identity**: identical
`(source_id, source_version)` ⇒ no new row.

The aggregate key is the **corroboration identity**: identical
`source_id` ⇒ same corroboration family; new `source_id` ⇒ new family.

`source_version` is REQUIRED (non-empty) on every ingest call. An
empty source version would defeat replay idempotency. The ingest path
returns a `sourceVersion required` error if the caller passes ''.

## 4. Replay proof

`test/historical-provider-evidence.test.js`:

- **P1** First ingest of `S/V1` → 1 sightings row, 1 aggregate row, DSC=1.
- **P2** Replay of identical `S/V1` snapshot → 0 new sightings rows,
  0 new aggregate rows, full state byte-identical, DSC still 1.
- **P5** `S/V1 + S/V2` → corroboration unchanged from `S/V1` alone.
- **P7** Shuffled order of multiple sources and replayed snapshots
  → identical logical state, identical projection.

100k-row synthetic perf test confirms replay is genuinely a no-op
(not just row-preserving): second pass sees `countHistoricalProviderSightings() === N`
and `countHistoricalProviderEvidence() === N` (no amplification).

## 5. Corroboration proof

- **P3** `S/V1 + S/V2` from one source → aggregate row has
  `distinct_snapshot_count = 2` but the projection still emits
  exactly ONE `PROVIDER_HISTORICAL` item per (provider, source_id).
- **P4** Independent `T/V1` from another source → second aggregate
  row, second `historicalSourceId`, corroboration ≥ 2.
- **P5** Same-source V1+V2 ≠ corroboration (no spurious family).
- **P6** Independent-source T/V1 > corroboration (real new family).
- **P10** `file_index_key = -1` vs `file_index_key = 0` remain
  distinct identities (no identity mutation).

## 6. Migration implication for the new table

The previous schema (single `historical_provider_evidence` with
`source_version` in PK) is replaced. In a fresh DB, nothing to migrate.

In an existing dev DB, the previous schema is replaced by:

```
old: historical_provider_evidence  (PK includes source_version, has observation_count)
new: historical_provider_evidence_sightings + historical_provider_evidence
```

Both tables are created with `CREATE TABLE IF NOT EXISTS` in `SCHEMA`.
For a dev DB that already has the old table, manual migration:

```sql
DROP TABLE historical_provider_evidence;
-- restart the cache; both new tables will be created.
```

There is no production data on this table (the previous slice added
the landing zone; no importer wires into it yet). The migration risk
is contained to development environments.
